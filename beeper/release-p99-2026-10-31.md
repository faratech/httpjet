# Current candidate versus the exact shipped release: p99

**Median scheduled p99 is lower in all ten tested cells than the shipped v0.1.10-11. H1 plaintext static is inconsistent: one of three paired cycles regresses 147.74%.** The other nine cells improve p99 in all three cycles. These results support a release comparison, with that H1 qualification; they do not establish regression-free latency under every run.

This fresh study ran only on SINGULARITY on 31 October 2026. It compares the retained, fully qualified repaired PGO application with a fresh download of the exact public release. The earlier [native HTTPS source-control study](native-tls-followup-2026-10-31.md) uses a separately rebuilt historical production-source PGO control; its static H2 regression remains a separate unresolved result.

## Same offered load, warm caches

Each of ten cells has three ABBA cycles: release, candidate, candidate, release. Every arm completes 60,000 measured responses plus 5,000 warmups, with a 1 KiB response and 15,000 offered requests/s. Both binaries retain their caches. The candidate also enables its page-response memo, plaintext H1 readiness/kernel serving, plaintext H2 kernel serving, and accelerated H3 with GSO 20/send batch 1. HTTPS H1/H2 use their native userspace paths. H3 uses userspace QUIC.

There are 32 connections, four streams per H2/H3 connection, one server worker pinned to CPU 8, observer CPU 10, and clients on CPUs 0,2,4,6,12,14. Source and destination are literal 127.0.0.2; the observed route is `lo`. TLS clients verify the fixture CA and expected protocol. Static means the warm static-serving case; page cache means a warm origin-page-cache hit, not a PHP execution time.

The table reports **median of six per-arm p99 values**, in milliseconds, for scheduled arrival to completion. It includes time waiting for client dispatch. It is distinct from a pooled request p99 or a capacity measurement. Negative changes mean lower latency.

The H1 static cycle-2 candidate outlier has 8.828 ms scheduled p99, 8.579 ms dispatch-lateness p99 and 0.401 ms service p99. Those quantiles describe separate distributions and must not be added. The counters do not establish a host-scheduling cause. H1 static therefore needs further confirmation before a consistent p99 improvement can be claimed.

Release H1 page-cache arms include 38.685 ms and 540.378 ms scheduled-p99 outliers; the latter achieves 13,169 requests/s. They remain in the dataset. No arms were excluded or rerun. The medians above and the paired cycle ratios use different groupings; their percentage changes need not match.

Bounded admission produced **31,713 waits across 52 arms: release 31,177, candidate 536**. H1 has 32 client slots; H2/H3 have 128. Waits are included in scheduled latency. All cell throughput medians are approximately 14,994–14,997 requests/s, but individual release arms can fall behind the offered rate. These are neither unrestricted open-loop results nor unloaded service latencies. [Per-arm records](../docs/evidence/release-p99-20261031/arms.csv) retain achieved rates, peak concurrency and admission counts.

## CPU is a separate measurement

Process CPU falls in all ten cells and every paired cycle. The measurement includes the helper for plaintext kernel arms. Whole-VM CPU is mixed: H1 TLS page-cache VM busy time rises 13.98% overall, with cycle changes +35.83%, +3.00%, −8.40%.

| Protocol | Fixture | Server/helper CPU change | Whole-VM CPU change |
|---|---|---:|---:|
| H1 plaintext | Static | -66.95% | -3.56% |
| H1 plaintext | Page cache | -76.30% | -18.49% |
| H1 over TLS | Static | -20.66% | -7.06% |
| H1 over TLS | Page cache | -43.60% | +13.98% |
| H2c plaintext | Static | -65.09% | -6.79% |
| H2c plaintext | Page cache | -76.84% | -5.48% |
| H2 over TLS | Static | -30.97% | -4.75% |
| H2 over TLS | Page cache | -58.04% | -25.81% |
| H3 | Static | -57.30% | -33.47% |
| H3 | Page cache | -44.36% | -23.46% |

Process CPU is user plus system time divided by all 65,000 responses in the client span, including warmup. PMU covers user-mode server/helper threads. VM busy time includes every Linux CPU's user, nice, system, IRQ and softIRQ time, including clients and unrelated work. Windows-host activity remains unobserved. Process improvements do not establish universal whole-system savings.

## Evidence and identity

All **120 arms, 7.2 million measured responses and 600,000 completed warmups passed**. The independent auditor recomputed 7.68 million raw timing rows and 866 PMU thread records; H3 raw TSVs contain measured rows, with warmup/status/body validation established by the pinned validating client, harness and summaries. All ten compiler monitors, body/status/protocol checks, client-headroom gates, PMU running coverage, cache/kernel coverage and clean exits passed. Source, profile, helper, tool and binary inputs match before and after. The owned process supervisor reports no remaining children or private-session processes.

The nine forum preview/test containers were stopped before this study. The explicit local Docker endpoint was empty at the input boundaries, and the post-run process check found no HTTPJet, compiler or QEMU workload. Compiler monitoring samples once per second; this does not prove the absence of shorter activity or Windows-host contention.
