# H2 PGO at matched lower load: native and kernel tradeoffs

Measured and published **31 October 2026**.

At an offered 15,000 requests/s, the PGO candidate in native H2 mode uses less process CPU than the exact release in both fixtures. Enabling kernel H2 on the same PGO build increases process CPU and the across-arm median service p99. Scheduled p99 moves in different directions for static and page-cache traffic. This is a matched-rate comparison, not a capacity ranking.

The [full release capacity matrix](pgo-release-2026-10-31.md) and [same-source PGO pilot](pgo-pilot-2026-10-30.md) answer separate questions. Native-candidate versus release results combine the candidate implementation, page-response memo and build/profile effects; they do not isolate PGO or Beeper alone. The native/kernel pair uses the same PGO binary and isolates the requested kernel option.

## Workload and completeness

All **36 arms**, **2,160,000 measured responses** and **180,000 warmup responses** validated. Every arm uses 60,000 measured requests plus 5,000 warmup requests, a 1 KiB body, H2c, 32 connections with four streams each, one server worker on CPU 8 and six client threads on CPUs 0,2,4,6,12,14. The observer runs on CPU 10. Both ends use `127.0.0.2` on SINGULARITY; the recorded route uses Linux loopback.

Each of the static and origin page-cache fixtures runs three symmetric `release, native, kernel, kernel, native, release` cycles. Existing caches are enabled and warmed; the candidate native/kernel arms both enable the finished page-response memo. PHP is disabled. The release receives no experimental arguments. The kernel arm uses the pinned privileged helper; unsupported input retains native ownership.

Admission is bounded at **128** concurrent requests. **7/36 arms reached that cap**, with **594 admission waits** across the complete run. These measurements are neither unrestricted open-loop load nor proof of continuous unsaturation. Failures, expiry and unattempted outcomes are checked; there are no retries or reconnects to hide them.

The static kernel group has a slightly lower across-arm median scheduled p99; the page-cache kernel group has a higher one.

Process CPU is server plus helper **user + system** time over the whole client span, including handshake, warmup, measurement, client output and teardown. The server’s later shutdown/drain is outside this span. Its denominator is **65,000 responses** per arm. It excludes kernel/IRQ work charged elsewhere. PMU instructions and cycles count **user mode only**, with the same 65,000-response denominator; they exclude kernel, IRQ and hypervisor work.

VM busy includes all Linux CPUs and clients/unrelated Linux work. The analyzer converts `user + nice + system + irq + softirq` ticks with each arm’s recorded `linux_cpu_ticks.ticks_per_second`: `busy_ticks × 1,000,000 / ticks_per_second / 65,000`. Windows host activity is unobserved. These process, PMU and VM measures have different scopes; none alone establishes whole-server CPU savings.

## Operational interpretation

For CPU-sensitive or service-latency-sensitive operation at this tested lower H2c load, prefer the native H2 path. Kernel H2 remains an opt-in capacity option with the CPU/latency costs shown here and in the full capacity matrix. This result does not establish an automatic rate threshold or change runtime defaults. Other rates, bodies, congestion, encrypted H2 and real application traffic require their own measurements.
