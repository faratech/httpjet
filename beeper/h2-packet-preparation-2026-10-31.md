# HTTPJet H2: restoring packet preparation in the certified fast path

The certified H2 matcher skipped a packet-preparation operation performed by the Beeper decoder. Under sustained load, a response-hook callback contained only part of a selected four-request batch and the connection failed closed. Restoring that preparation, together with an idempotent fatal path, passed the subsequent correctness stress campaign. CPU savings and p99 behavior still require qualified performance measurements.

The decisive evidence came from an owned BPF-map capture before helper cleanup. The selected batch required 92 input bytes for four HEADERS frames and 4,664 output bytes. Its SK_MSG callback contained 46 input bytes. Diagnostic mask `2` identified only the size mismatch: the captured phase was ACTIVE, the size was nonzero, and the response bound was valid. The registration tag matched the connection. Four current records carried fatal code 122; `selected=4236`, while `mutated=redirected=4232`. Those requests failed before response mutation. Repeated copies agreed, although the capture was not atomic. The client retained four broken-pipe failures after 125,334 successful measured responses. [Red snapshot](../docs/evidence/h2-packet-preparation-20261031/red-snapshot.json).

Source inspection explains the missing preparation. Beeper's frame parser conditionally pulls enough bytes to read a frame header. For HEADERS, it then unconditionally pulls through `offset + frame_length` before decoding the payload. When the final accepted frame is HEADERS, that operation makes the entire selected skb linear. The certified shortcut used `bpf_skb_load_bytes` for its header and exact-block checks, leaving out this buffer-shape side effect. Its HPACK certificate checks did not replace the preparation requirement. The decoder performed the needed operation; HTTPJet's integration shortcut discarded it.

WINDOW_UPDATE needs a qualification: the baseline parser returns after describing its header, before the full-payload pull. A batch ending with WINDOW_UPDATE could therefore retain four trailing payload bytes outside the linear area. The repair establishes the full-buffer invariant for every selected batch, covering that inherited gap as well.

The fix calls `bpf_skb_pull_data` for the complete, bounded skb after input/ring checks and before parsing, pins, flow-credit changes, logs or redirection. Failure returns the untouched request to native with existing reason 9. No direct packet-data pointer survives the call. Cookie, generation, exact-block identity, gate, flow-control and response checks remain. Restoring this preparation preserves the existing response path without introducing a corking protocol for this regression.

Fatal handling also needed to become idempotent. Previously, another queued callback could revisit the failed batch, overwrite `last_fatal` with 122 and release its pins again. The repair drops already-FATAL callbacks and guards the fatal routine, preserving the first H2 error and avoiding repeated release. It does not attempt to release every later batch without proving quiescence.

The repaired helper `0e7be72d…`, containing serving ELF `4bdf891e…` from H2 source `0cd1e3a8…`, completed twenty static 1 KiB stress arms: **10,000,000 measured responses and 200,000 warmup responses**. Every measured body matched; every run recorded positive H2 offload and zero H2 kernel failures. These are correctness results. The observer detected concurrent compiler activity, attributed by the coordinator to an unrelated Dockerforum build, so the campaign supports no RPS, CPU or latency-gain claim. [Regression receipt](../docs/evidence/h2-packet-preparation-20261031/regression-receipt.json).

The H2 protocol, certificate-control, certificate-candidate, expiry and lifecycle steps passed, including dynamic-table replacement/clear, expiry and lifecycle coverage. Overall qualification remains false after the H1/UA stage encountered an existing 100 ms registration-timeout lifecycle problem. That separate issue has red/green unit validation; whole-application conformance and fresh PGO remain pending. [Partial qualification](../docs/evidence/h2-packet-preparation-20261031/partial-qualification.json), [H1 unit validation](../docs/evidence/h2-packet-preparation-20261031/h1-unit-validation.json).
